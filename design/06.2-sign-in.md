# 6.2 Sign-in and accounts

- **No passwords.** Sign-in is a six-digit code sent by email (ten minutes, five attempts, single use), or a **passkey**
  (built into ASP.NET Core Identity in .NET 10). Nothing to leak, reuse or stuff.
- **A code belongs to the address, not to a browser.** It can be read on any device and typed into any browser, so a
  person can register on someone else's computer with the mail open on a phone, and later ask for a new code on their
  own device. A new code replaces the earlier one; the email and the page say to use the newest.
- **How many codes.** For one address, all browsers that have not signed in to that account before share five codes an
  hour and ten a day (`SignIn:CodesPerHour`, `SignIn:CodesPerDay`). The daily limit is what bounds guessing: at most 50
  tries a day against one account, about a 2 % chance over a year of constant attack, against about 20 % with the hourly
  limit alone. Beyond either limit nothing is sent, and the answer does not say so.
- **Known browsers.** The shared limit can be used up by anyone who knows an address, which would keep that person from
  signing in by code. So a browser that has signed in to an account keeps a one-year `__Host-` cookie with a random
  identifier (stored hashed, tied to that account; it gives no access by itself). Such a browser has its own five codes
  an hour and ten a day, the same two settings counted separately, and a code it asked for is accepted only from it, so
  requests and wrong guesses from elsewhere cannot cancel or exhaust it. Codes asked for from any other browser stay
  usable anywhere, as above. A stranger can then block sign-in by code only from browsers the person has never signed in
  with; the usual browser and a passkey keep working. Details in 8.20.2.
- **Registration = email only.** Accounts are confirmed by email (owner, 2026-11-19); there is no phone check (SMS
  verification is a paid service, charged per message and a target for SMS-pumping fraud) and no sign-in through Google,
  Apple or Facebook. Each account has a **verification level**: `email` once the address is proven. The form says so in one
  line under it, with no date and no sign-up for the wallet (`SignIn.Verification`).
  **Not built.** The EU Digital Identity Wallet as a "verified person" level that existing people could complete as an
  upgrade, once the wallet is available in Lithuania (the EU deadline is 24 December 2026; no national date is announced),
  with counts reported by level. It stores nothing more than the wallet proves is needed: that the person is 18 or older,
  and a pairwise pseudonymous identifier to keep one account per person, never a personal code.
- Email alone lets one person create many accounts for nothing. What stands in for a stronger check:
  - registration is **by invitation** while `Registration:RequireInvitation` is on (the default): a code from the team,
    from a member or from an organisation (8.14.14). A valid MP office member's invitation (8.5.3) counts as one: a
    person who comes by it registers on the office page with no invitation code; the server checks it at registration
    and again at completion (known, unused, unexpired, made by the account that is still the MP's), registering does not
    use it up (accepting it does), and the account keeps only a level, one below the MP's account, as an organisation's
    code leaves only its level (8.14.14). Such a registration is in no invitation code's count or daily series on the
    administrators' screen, there being no code; it is not counted as "without a code" either, since it has a level. An
    MP's official address may register without an invitation while `Registration:OfficialAddressesWithoutInvitation` is
    on (off by default; 8.5.1);
  - one account per **normalised address** (lower case, the `+tag` part removed, dots ignored where the provider ignores
    them), and addresses at disposable-mail domains are refused (`email.disposable`);
  - per-IP limits on registration (6.4), and a bot check: a proof of work the browser does by itself, sent with a registration and with every request for a sign-in code by email (below);
  - the 30-day count beside every number, and the surge note (6.6).
- **Bot check (design 6.4).** Registering, and asking for a sign-in code by email (also asking again), carry a solved proof of
  work in the request's `botCheck` field. Nothing for the person to do: the site's own script (`js/lt2-botcheck.js`) fetches a
  challenge (`GET /api/v1/bot-check/challenge`) and solves it in the background as soon as the form is shown, so the result
  is ready before the button is pressed; only if the work takes longer than about 0.4 s does the form say, quietly,
  "Tikrinama, ar jūs ne robotas…". A refusal of the proof alone (it was used, or has expired) is answered by a new solution
  and the same request once more, without a word; a second refusal shows `bot-check.failed` ("Nepavyko patikrinti, ar jūs ne
  robotas. Bandykite dar kartą."). The proof is checked **first**, before the address, the invitation or any limit by address is
  looked at, and there is one answer, 400 `bot-check.failed`, whatever the address (registered, pending, unknown) and whatever
  else is wrong with the request, so it reveals nothing about an address. It is **not** asked for: signing in with a code or a
  passkey, typing a code, and changing the email address (those run in a signed-in account that passed it at registration, under
  its own limits, 6.4). Without JavaScript neither registration nor asking for a code works at all (the forms are islands whose
  controls stay disabled until WebAssembly runs, and say so), so there is no path without a proof to loosen: nothing extra
  is done for it. `BotCheck:Enabled` (on) switches the check off, `BotCheck:MaxNumber` and `BotCheck:ChallengeMinutes` tune it (5.6).
- **An account is pending until its address is proven.** Registration takes the address and the invitation code and
  creates a pending account: no name, no declarations, no role, nothing it can do. The first correct code proves the
  address. Only then is the person asked for the display name and the declaration of being 18 or older, only then is
  the invitation use counted (if it has run out by then, the person is told so and can enter another), and with the
  declaration the account becomes a member. So nobody can attach a name or an age declaration to someone else's
  address, or use up an invitation with addresses they do not control.
  - Asking for a sign-in code for a pending account works like any other and completes the registration, on any
    device.
- **Changing the display name.** A member changes the name on the account page ("Profilis", 8.21) with the profile's
  one form, `PUT /api/v1/me/profile` (8.28.5), with the registration's rule: at most 60 characters, empty allowed (what the person
  wrote then shows "Lietuva 2.0 naudotojas"; a public profile's name cannot be emptied, 8.25.6). The name is read live
  wherever it is shown (beside arguments, in an organisation's list of representatives, on feedback and moderation
  screens), so a change shows everywhere at once, older arguments included; summaries never hold names, so their
  snapshots are untouched. There is no limit on how often the name changes; the shared per-account request limit
  (`RateLimits:Participation`) only guards against a runaway script.
  - A writing restriction (8.3) also blocks changing the name (`writing.restricted`), since the name is text others
    read; Identity asks Appeals through `IWritingRestrictions` (SharedKernel).
  - The change is audited that it happened (`profile.display-name-changed`), never from what to what; nothing public
    says a name was changed; no earlier names are kept.
- **Changing the email address.** The Lithuanian texts are drafts for the native reader. A member changes the
  account's address on "Saugumas ir duomenys" (8.21), in a part "El. pašto adresas" (`#el-pastas`) that shows the
  address in use and "Keisti adresą". An account has one address: there is no second one (a passkey is the second way
  in when the mailbox is lost), and the address stays unique, one account per normalised address.
  - *Proving it is them first.* A stolen session must not be enough to move an account, so the change starts only in a
    passkey session (made in place by "Patvirtinti prieigos raktu", `PasskeyStep`, as above) or after a code sent to the
    address in use, typed in the same form (the account's sign-in code with its limits, in an email that says what it is
    for). A staff account needs a staff-passkey session with a fresh confirmation; the
    MP's own account (8.5.4) a passkey session, as for everything it does.
  - *Proving the new address.* The person types the new address; a six-digit code goes to it, with the rules of a
    sign-in code (ten minutes, five attempts, single use, the newest replaces the earlier ones) and counted against the
    new address's code limits. The address changes when the code is typed in the session that asked
    (`POST /api/v1/me/email/change` with the address, then `POST /api/v1/me/email/confirm` with the code; the code in the
    body). The new address must differ from
    the one in use once normalised, and a disposable-mail domain is refused (`email.disposable`), as at registration.
  - *An address that is taken.* The form's answer is the same whether the new address is free or not ("Kodą išsiuntėme
    adresu …"), since responses never reveal whether an address is registered. If another member's account has it, the
    email to that address says that it already belongs to an account and that nothing was changed; no code is in it. An
    address held only by a pending account (never proven, 6.2 above) is not taken: confirming the change proves it, and
    the pending account is deleted, as it would be after seven days.
  - *What changes with it.* Every email made after the change goes to the new address, and a code already sent to the
    old one stops working. The session that made the change goes on under a new key; the account's other sessions end,
    as when a passkey is removed. Passkeys and known browsers (8.20.2) stay, being the account's, not the address's. The
    MP part follows the new address by the rule of 8.5.1: an official address gets the offer to take the profile over;
    a link already made stays (it is to the person, 8.5.2), and the MP's mail goes to the official address from the open
    data whatever the account's address is. Invitation codes and their counts are unchanged.
  - *The old address is told.* An email to the old address says that the account's address was changed, when, and to
    which address in part (`r***@pavyzdys.test`), with "Ne jūs? Grąžinti ankstesnį adresą": a one-time link, good for
    seven days, its token after the `#` and stored hashed. Opened in any browser, its page puts the old address back with
    one press (a mail program that opens links ahead changes nothing), ends every session of the account and asks the
    person to sign in again; the new address is then told so. Using one such link ends the account's other links. If
    another member's account has the old address by then, the link does nothing; an account only pending on it goes, as
    above. Every link that does not work gets one answer. The link works without a session and without the terms
    accepted (`TermsExemptions.Routes`), like the members' stop links.
  - Audited that it happened (`account.email-changed`, `account.email-restored`), never the addresses; nothing about it
    is public; the export holds only the address in use. Logs carry no addresses, as everywhere.
- **Personal invitation codes.** Every member has one personal code, made at completed registration (or when first
  needed), shown on the account page as a link to the registration form with the code filled in and as a short code
  with a copy button. Format: eight characters from 29 that cannot be mistaken for one another
  (`23456789ABCDEFGHJKMNPQRSTVWXYZ`: no 0, 1, I, L, O, U), shown as `XXXX-XXXX`; case, dashes and spaces do not matter
  when typed; about 5 × 10¹¹ codes, and guessing stays under the registration rate limits. Codes are never written to
  logs.
  - Uses per personal code are a runtime setting, `Registration:PersonalCodeUses`, 0 = no limit, the default. Team codes
    keep their own uses and expiry.
  - The member can replace the code: a new one is made, the old one stops working, and the member's count (the sum of
    their codes) carries over.
  - A use is counted when registration completes, on a counter on the code and in daily totals per code; the count never
    drops when an invited person deletes their account. The profile keeps which code it registered with, and that goes
    with the account.
  - When the inviter deletes their account, their codes are switched off and lose their owner: nothing of the person
    stays on them; their counts, levels and daily totals stay as anonymous numbers.
  - The member sees only how many people completed registration with their code and whether it is on; no names, dates
    or list. The registration form says plainly that whoever gave the code sees that it was used, not by whom.
  - Administrators (staff-passkey session) get a page, `/administravimas/kvietimai`: completed registrations per day, in
    total and for the codes that brought the most people, as a server-rendered chart with the numbers also as a table;
    those codes (team codes by their code, personal codes by the member's display name); and the numbers per level
    (level 1: by team codes or with no code; level 2: by codes of level-1 people; and so on). No who-invited-whom tree and
    no list of who used a code. An administrator can switch any code off and on again, with a statement, audited; a
    member whose code was switched off sees that on the account page, with the contact address, and cannot replace it
    meanwhile.
  - A code that does not work gets one message on the registration form, whatever the reason (unknown, switched off,
    replaced, expired, used up): ask whoever invited you for a new one.
  - Never combined with sides: no screen, API answer, export or query joins invitations with positions, marks or
    arguments. No ranking shown to members, no rewards, nothing public. An account restricted from writing (8.3) keeps
    its code; switching a code off is a separate action.
  - If the address already has an account, registration only sends a sign-in code to the address on the account; what
    was typed is discarded.
  - Accounts still pending after seven days (`Registration:PendingAccountDays`) are deleted by the maintenance job that
    also removes old codes and expired sessions, so an address typed by a stranger is not kept.
- Reading needs no account. Taking a side, writing a reason and endorsing need a confirmed email and the age
  declaration.
- **Minimum age: 18, self-declared when the address has been confirmed.** The signal is compared with a parliament
  elected by adults; the EU Digital Identity Wallet could later confirm it.
- Session: `__Host-` cookie, `Secure`, `HttpOnly`, `SameSite=Lax`, sliding 30 days; a person can see and end their
  sessions. No tokens in the browser: the WASM client uses the same cookie (same origin).
- **A session is what it was signed in as.** Every sign-in (an emailed code, a passkey, the take-over of an MP's
  profile, the office invitation's passkey, a code session becoming a passkey or staff session) starts a new session
  under a new key; the browser's session before it, of the same account or another, ends as by signing out (its row is
  deleted, its cookie leads nowhere). After that the session's account, its way of signing in and its passkey never
  change: renewing it (the sliding expiry, the security stamp's check every 30 minutes, the registration's completion)
  keeps them, so a passkey session stays a passkey session for its 30 days. A changed security stamp still ends the
  session.
  - *Never a silent switch.* A sign-in in a browser signed in to another account says so: its answer carries
    `accountChanged`, and the sign-in steps show "Prisijungėte kaip kitas narys: {vardas}." (the new account's display name
    in the nominative after a colon; without a name "Prisijungėte kaip kitas narys.") with "Tęsti" before going on. The
    other account's kept analytics comparison goes with its session (8.26.6). The take-over and the office invitation's
    acceptance stay tied to the signed-in account; a passkey of another account is refused there.
  - *A passkey session in place.* Where an action needs a passkey session (speaking for an MP, a linked account's passkey
    change) and this one was signed in by a code, the island says "Šiam veiksmui reikia prisijungimo prieigos raktu." with
    "Patvirtinti prieigos raktu" (`PasskeyStep`): an assertion with one of the signed-in account's own passkeys makes the
    session a passkey session under a new key (`POST /api/v1/me/passkey-session`), counted as just confirmed, audited
    (`passkey.session-started`, without the address), no email; then the island reads its state again. With the staff
    passkey it is a staff session too (audited `staff.session-started`). A passkey of another account is refused with
    `passkey.other-account` and changes nothing; the browser stays signed in to its own account.
- **Staff** (moderator, administrator). A staff role works only in a session signed in with a **staff passkey**. A
  session signed in by email code is an ordinary member session, whatever roles the account has, so getting into a
  staff member's mailbox is not enough.
  - *Activation.* An administrator grants the role; the system shows a one-time activation code on the administrator's
    screen (sixteen characters in groups of four, valid 24 hours, never sent by email), and the administrator passes it
    to the person directly. The person signs in with a passkey and enters the code: that passkey becomes the staff
    passkey, and any other passkey on the account is removed.
  - *Afterwards.* Adding or removing a passkey on a staff account needs a staff-passkey session and a fresh passkey
    confirmation (within the last ten minutes). Sensitive actions (approving an urgent summary, changing roles,
    resetting an account, locking or unlocking an account, saving a runtime setting, ending an MP's link, sending the introduction letter) ask for the
    same fresh confirmation: without it the server refuses with `passkey.confirmation-required` and nothing is done; a
    screen that offers the action asks for the staff passkey on the same press and sends it again, keeping what was typed.
  - *A staff session without signing out.* A session on a staff account that is not a staff session (signed in by
    email code, or with another passkey) becomes one by an assertion with the account's staff passkey on
    `/prisijungti/raktas` (`POST /api/v1/me/staff-session`), reached from the account item (8.21), or in place by
    "Patvirtinti prieigos raktu" where a staff screen refuses and on the account page (the same `PasskeyStep` as above,
    with the staff passkey). Only the signed-in account's own staff passkey counts: another account's passkey, another
    passkey of the account, or an account without an activated staff role is refused with one answer
    (`passkey.staff-required`) and changes nothing. The session gets a new key: the old session ends and a passkey
    session takes its place, so the old cookie leads nowhere and the sessions list shows one session for the browser.
    It counts as a fresh confirmation. It is audited (`staff.session-started`, without the address); like a staff
    passkey sign-in, it sends no email.
  - *Lost passkey.* An administrator resets the account: its passkeys are removed, the sessions signed in with them end,
    and the role is inactive until a new activation code is used. The first administrator, and a lost last one, are
    activated from the server: the migrator command grants the role and prints the activation code.
  - Every grant, activation, reset and passkey change is audited, and the person is told by email.
  - *A locked account* (an administrator's full lock, 8.3) cannot sign in at all: a code request is answered and sends
    nothing, a typed code and a passkey are refused with the ordinary invalid answers, and the lock ends every session. The
    account is not told by a different answer, so nothing reveals whether an address is registered or locked.
- **Politicians** (verified MP, office member) need a passkey as well. Their proof of identity is the official
  `@lrs.lt` mailbox, so the take-over link plays the part of the activation code: the passkey is created while using
  the link, and later changes need that passkey or a new link. The details are in 8.5.2 to 8.5.4.
- **Other members:** a passkey is a convenience. The mailbox is what proves who they are, and a code still signs them
  in. They are told by email when a passkey is added or removed.
- No authenticator app: one way in to secure. It can be added if an MP's office cannot use passkeys.
- Responses never reveal whether an email is registered.
- **Local development: raised limits.** Locally the per-IP rate limits are raised through `deploy/.env`; the defaults in
  code and in production stay.
- **Not built. Local development only: a fixed sign-in code.** For hand testing on the local stack, one configured
  six-digit code may be typed in place of the emailed one, for any account. Guards, all of them: it is configuration
  only (an environment variable in `deploy/.env`), never a runtime setting and never on the settings screen, so no
  administrator can switch it on; the web host refuses to start when it is set and the site's own address
  (`Site:Address`, from the same `LT2_SITE_ADDRESS` Caddy serves) is not `localhost` or a `.localhost` host, and each
  request must also come to such a host; unset by default, and then it is refused like any wrong code. The real code is
  still generated, emailed and accepted. The fixed code works only where an emailed code does (registration and
  sign-in, a code requested and not yet used, expired or exhausted) and gives an ordinary member session; it never
  activates a staff role and has nothing to do with activation codes or passkeys. The sign-in page says plainly that it
  is on, and start-up logs one warning line (without the code). Building it needs the owner's own go-ahead, as it is an
  authentication bypass.
